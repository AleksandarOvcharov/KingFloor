# KingFloor domain — етажна собственост

This is the product built on top of the hackathon template described in the
rest of this repo's docs. Everything in `apps/web/app/building/*`,
`apps/web/app/api/building/*`, `apps/web/hooks/building/*`,
`apps/web/lib/building/*`, and `database/scripts/kingfloor-schema.sql` is
KingFloor-specific; everything else (auth, AI chat, analytics, i18n
infrastructure) is unmodified template plumbing it's built on.

## What was removed to make room for it

The template's generic marketing pages (`/features`, `/about`), the AI chat
page (`/ai`), and the analytics dashboard page (`/dashboard`) were deleted
from `apps/web` — they were unrelated to etажна собственост and `/building`
replaced `/dashboard` as the post-login home. Their backend routes
(`/api/ai/*`, `/api/analytics/*`) and shared types were **not** deleted:
`apps/mobile` still calls them for its own AI chat / dashboard screens.
Only the web-only consumers were removed: `apps/web/hooks/useAI.ts`,
`useChatHistory.ts`, `useSpeechToText.ts`, `useAnalytics.ts`, and the
dashboard-only chart components. `apps/web/app/api/ai/config.ts` (the AI
chat system prompt, still used by the API) was reworded to describe
KingFloor instead of the old generic template.

## Demo data

`database/scripts/seed-kingfloor-demo.sql` seeds one full demo building
(8 units, two months of fees in a mix of paid/unpaid/overdue, 12 expenses
spread over the last 4 months across several categories, 3 announcements,
an open poll with votes, 4 maintenance issues) for a specific
already-signed-up email — edit `v_admin_email` at the top and run it once.
A commented-out cleanup block at the bottom deletes that demo building so
you can re-seed from scratch.

## Joining a building

Being the creator/admin was originally the only way into a building — now
`/building/setup` has two tabs: "I'm the building manager" (the original
create-a-building form) and "I'm a resident" (self-service join by code, no
admin approval step). Every `buildings` row has a 6-character `invite_code`
(generated by a DB default, see `kingfloor-schema.sql`); the admin finds and
shares it from a card on `/building`. A resident enters it on `GET
/api/building/lookup?code=`, which returns the building plus the units with
no resident yet, picks one, and `POST /api/building/join` creates their
`building_members` row directly. `building_members.unit_id` has a DB-level
`UNIQUE` constraint so two residents can never land on the same apartment,
even via a race between this flow and the admin's by-email assign flow in
`/api/building/members`.

## Layout

`apps/web/app/building/layout.tsx` is a left sidebar (desktop) / horizontal
pill nav (mobile) shell, not the top-tab bar from earlier — `/building`
itself is now a role-aware dashboard: admins get the finance overview
described above, residents get a simpler "my unit + outstanding fees" view
(`AdminDashboard`/`ResidentDashboard` in `apps/web/app/building/page.tsx`).
The admin's invite code moved from a dashboard card into the sidebar itself
(desktop only, next to the role badge).

**Performance:** every `/building/*` page used to call `useBuilding(user)`
independently, so navigating between e.g. Fees and Issues re-fetched
`GET /api/building` from scratch each time. `apps/web/hooks/building/BuildingContext.tsx`
now fetches it once in a provider wrapping the whole layout
(`BuildingProvider`/`useBuildingContext()`); every page reads the same
cached membership instead of re-fetching it. Page-level `useAuth()` calls
that existed only to feed `useBuilding(user)` were removed along with it.

## Model

One organization = one **Building** (сграда), made directly of **Units**
(апартаменти) — no entrance/вход layer; each building is a single entrance.
A user has at most one **BuildingMember** row — one building per user in
this MVP — with role `admin` (домоуправител) or `resident`
(собственик/живущ), optionally linked to their own unit.

Run `database/scripts/kingfloor-schema.sql` after `fresh-database-setup.sql`
to create the tables, RLS policies, and the `handle_new_building` trigger
that auto-promotes a building's creator to its admin.

## Modules (MVP scope)

- **Units** (`units`) — full CRUD for admins: `POST`/`GET /api/building/units`
  plus `PATCH`/`DELETE /api/building/units/[id]`. Deleting a unit cascades to
  its `fees`/`poll_votes` (gone with it) but only clears the link on
  `maintenance_issues`/`building_members` (`ON DELETE SET NULL` — an issue or
  a resident's membership survives, just loses that apartment). Assigning a
  resident (`POST /api/building/members`) and removing one
  (`DELETE /api/building/members/[id]`, blocked for admins) are the
  `building_members` side of managing a unit's occupancy.
- **Fees & payments** (`fees`, `payments`) — admin generates a monthly fee
  per unit (fixed amount or per m²), marks fees paid/unpaid; each paid fee
  logs a `payments` row for history. Residents see only their own unit's fees.
- **Announcements** (`announcements`) — admin posts, edits, (un)pins, and
  deletes (`PATCH`/`DELETE /api/building/announcements/[id]`); every member
  reads.
- **Voting** (`polls`, `poll_options`, `poll_votes`) — admin opens a poll
  with 2–8 options; one vote per **unit** (not per person), matching how a
  real общо събрание counts. Admin can close or delete a poll (deleting
  cascades to its options/votes). **Each option** (not the poll as a whole)
  can carry its own document attachment
  (`poll_options.attachment_url`/`attachment_name`), uploaded to the public
  `poll-attachments` Storage bucket — e.g. three contractor quotes, one per
  option, for residents to compare before voting.
- **Maintenance** (`maintenance_issues`, `maintenance_comments`) — any
  member reports an issue and comments on it (thread shown inline, collapsed
  behind a "N comments" toggle on each issue — `useIssueComments` /
  `GET`+`POST /api/building/issues/[id]/comments`); transparency over
  privacy is a deliberate hackathon-scope call, so every member sees every
  issue and its full thread, not just their own. Admin changes status
  (open → in_progress → resolved).
- **Settings** (`buildings.name`/`address`/`iban`) — admin-only
  `/building/settings`, backed by `PATCH /api/building`. The `iban` column
  existed since the first schema but had no UI anywhere until this; it's now
  shown to residents on the Fees page so they know where to transfer money.
- **Expenses** (`expenses`) — the building's own spending (касова книга):
  admin logs a category/description/amount/date; together with `payments`
  (money in) this drives the admin dashboard's cash balance and
  income-vs-expense chart. `GET /api/building/finance-summary` is the single
  admin-only aggregate endpoint behind `/building` (cash balance split by
  payment method, this month's expenses by category, a 6-month income/expense
  series, and a per-owner dues table with a `paid`/`partial`/`unpaid` status
  derived from that owner's full fee history — not persisted anywhere, just
  computed from `fees`/`payments`/`expenses` on each request).

Not in scope yet (deliberately, per hackathon scoping): true partial-payment
amounts on a single fee (status is still binary per fee; "partial" at the
owner level is an aggregate across several fees), meeting-minutes storage
beyond poll attachments, multi-building admins, a tenant/owner permission
split (both are just `resident`).

## Auth model

All `/api/building/*` routes use `supabaseAdmin` (service role) plus an
explicit role check via `apps/web/lib/building/membership.ts`'s
`getMembership()` / `requireAdmin()` — mirroring `api/profile`'s pattern,
not RLS-via-anon-client. The SQL file's RLS policies are still real and
enforced (defense in depth / safe for any future direct-client reads), but
authorization for the mutations above lives in the route handlers.

## Adding a feature

Follow the existing module's shape: a Zod schema in
`packages/shared/src/schemas.ts`, a type in `packages/shared/src/types.ts`,
a route under `apps/web/app/api/building/`, a hook under
`apps/web/hooks/building/`, strings in the `building` namespace of
`packages/shared/src/i18n.ts`, and a page under `apps/web/app/building/`.
Mobile has no KingFloor screens yet — when it gets one, call the same
`/api/building/*` routes via `apiFetch()` (§3 pattern 1 in the root
`AGENT.md`), don't reimplement.
