Not a code bug; fixed by actually merging and pushing (which step 8 already describes) and telling them to reload Expo Go.
10. **Bug fix, direct to `main`**: user reported "above the map is all white even in dark mode." Real root cause, **worth internalizing**: the `WebView` loading `/embed/map` is a separate browser context with its own fresh `localStorage` — it has no idea what theme the native app is in. Fix: `map.tsx` now passes `?theme=dark|light` in the embed URL and remounts the `WebView` (`key={theme}`) on change; `embed/map/page.tsx` reads it **server-side** (it's an `async` page component receiving `searchParams`) and applies `.dark` to `<html>` via an early inline `<script>`. The first attempt — applying `.dark` to a wrapper `<div>` instead — silently failed and revealed a real Tailwind v4 subtlety: `--color-background: hsl(var(--background))` (what `bg-background` etc. resolve to) is computed *once*, inherited from `:root`; overriding `--background` on a descendant doesn't retroactively change an already-inherited `--color-background`. The class has to land on the actual root. This is now documented in `docs/mobile.md` and `apps/web/AGENT.md` — read it before touching any dark-mode logic on a route that isn't the main app shell.
11. **Full documentation overhaul**, requested explicitly ("carefully look through all documentation... make it agent first... update ALL md files, README.md included"). ## Gotchas worth knowing before you touch things

- **The dark-mode-via-WebView bug (item 10) will bite again** if anyone adds a second `apps/web/app/embed/*` route for mobile to load — the fix isn't automatic, each embed page needs its own `?theme=` param handling and its own early inline script applying `.dark` to `<html>`. Copy the pattern from `embed/map/page.tsx`, don't reinvent it, and don't try the wrapper-`<div>` approach — it silently does nothing, for the Tailwind v4 reason explained in item 10.
- **If a mobile feature 404s or behaves unexpectedly against production**, check `apps/mobile/.env`'s `EXPO_PUBLIC_API_URL` and whether the relevant branch is actually merged + pushed + deployed before assuming it's a code bug (item 9). This will keep happening as long as testing happens against the live Vercel deployment instead of a local dev server.
- **Where documentation now lives** (post item 12): monorepo-wide stuff → root `AGENT.md`/`CLAUDE.md`/`README.md`. Web-specific → `apps/web/AGENT.md`/`README.md`. Mobile-specific → `apps/mobile/AGENTS.md` (note: plural, not `AGENT.md`) + `apps/mobile/README.md`, with the deep architecture writeup in `docs/mobile.md`. If you're about to add project documentation and aren't sure where, check whether the content is genuinely shared (both apps care) or app-specific — don't dump everything back into the root files.
- Everything from handoff-01's gotchas section (the pnpm shebang-shim issue, `@types/react` pinning, Expo SDK pinned to 57, `.npmrc`'s `node-linker=hoisted`, the Android SDK being environment-specific leftover from an earlier Capacitor phase) is still accurate and still applies — not re-copying it here, go read handoff-01 if you hit any of those.
